## 17.1 The Question Behind the Chapter

A Python program that runs and prints a result is a *program*. A Python program that *waits* — that sits listening, accepts requests from other programs over the network, does work on their behalf, and sends responses back — is a *service*, and almost every system a staff engineer builds or operates is, at bottom, a collection of services. This chapter is about that transformation: how a program becomes a service, what stack of abstractions sits between a raw network socket and a clean `async def` request handler, which web frameworks exist and which to choose, and — the part that genuinely separates a demo from a production system — the operational concerns that an engineer who has only ever built demos does not know to think about.

The chapter has a spine, and it is worth naming up front because it runs through every section: **a service lives in a hostile environment.** The network is unreliable. Other services it depends on will be slow or down. Clients will send malformed requests, too many requests, requests that never finish. A program assumes a benign world; a service must assume a hostile one, and the difference between code that works in a demo and code that survives in production is, almost entirely, the difference between those two assumptions. We will build up from the raw socket to the framework, and then spend the back half of the chapter on hostility — timeouts, backpressure, circuit breakers, idempotency, graceful shutdown — because that is where the staff-level knowledge lives.

## 17.2 The Foundation: Sockets and TCP

Underneath every web framework, every HTTP library, every service, is the *socket* — the operating system's primitive for network communication. You will rarely write socket code directly; the abstractions above are good and you should use them. But you must understand what is underneath, because the abstractions *leak* — when something goes wrong at the network level, the symptom surfaces in your framework code, and you cannot diagnose it without knowing what the framework is sitting on.

A **socket** is an endpoint for communication — an object representing one end of a network connection. The dominant protocol for services is **TCP** (the Transmission Control Protocol), and TCP makes a specific and valuable set of guarantees: it is *connection-oriented* (two endpoints establish a connection, exchange data, and close it), it is *reliable* (data sent is data received, or you are told of the failure — TCP retransmits lost packets), and it is *ordered* (bytes arrive in the order they were sent). Those guarantees are why TCP underlies HTTP and almost everything else; they are also not free, and the alternative, UDP, trades them away for lower latency where reliability and ordering are not needed.

The TCP connection lifecycle has a shape worth knowing because its terms appear in real diagnostics. A server *binds* to a port and *listens*; a client *connects*; the two complete a three-step handshake to establish the connection; data flows; and the connection is *closed*, which is itself a multi-step exchange. The thing to retain: establishing a TCP connection *costs* — it is a network round-trip (or several, more if TLS is layered on top, Section 17.6), and a round-trip is *slow* relative to computation, often milliseconds. This single fact — connections are expensive to establish — is the entire reason for *connection pooling*, which Section 17.5 will make central. A service that opens a fresh connection for every request is paying that round-trip cost every time, needlessly.

The leak that most often surfaces: a service "hangs," and the cause is a socket-level wait with no bound on it — a connection that was established and then the other end went silent, and your code is sitting in a `recv` that will never return because nothing is coming. That is not a framework bug; it is the absence of a *timeout* on a network operation, and it is the single most common production-Python failure. Section 17.5 makes the rule; the foundation for understanding *why* the rule exists is here: a network operation can wait forever, because the network can simply not answer.

## 17.3 HTTP, WSGI, and ASGI

Most services speak **HTTP** — the request/response protocol of the web. An HTTP interaction is, in essence, simple: a client sends a *request* (a method — `GET`, `POST`, `PUT`, `DELETE` — a path, headers, and optionally a body), and the server sends a *response* (a status code — `200` for success, `404` for not found, `500` for server error, and the rest — headers, and a body). HTTP is *stateless*: each request is independent, carrying everything needed to handle it; the protocol itself remembers nothing between requests. Statelessness is a deliberate and valuable property — it is what lets you run many identical copies of a service behind a load balancer, since any copy can handle any request — and it means that any *state* a system needs (a user's session, say) must be carried explicitly, in the request or in a shared store, not held implicitly in a server's memory. (This connects directly to Chapter 21's deployment story: stateless services scale horizontally; stateful ones do not, easily.)

Between the raw HTTP and your Python code sits a *protocol interface* — a standardized contract for how a Python web application receives a request and returns a response. Python has two, and the distinction is exactly the synchronous/asynchronous distinction of Part IV.

**WSGI** (the Web Server Gateway Interface) is the *synchronous* contract, and the historical one. A WSGI application is, at bottom, a callable that receives a request's data and returns a response. WSGI is synchronous — one request, handled start to finish, by one worker — and it is what the traditional frameworks (Flask, classic Django) speak. WSGI servers — `gunicorn` is the common one — run a pool of synchronous workers, each handling one request at a time.

**ASGI** (the Asynchronous Server Gateway Interface) is the *asynchronous* successor. An ASGI application is an `async` callable, and ASGI is built for the event-loop model of Chapter 14 — one worker, on one event loop, handling many concurrent requests by interleaving them at their `await` points. ASGI is what the modern async frameworks (FastAPI, Starlette) speak, and ASGI servers — `uvicorn` is the common one — run async workers.

The choice between them is Chapter 13's decision in a new costume. A WSGI/synchronous service is simple and entirely adequate for many workloads; it handles concurrency by running multiple worker *processes*, and for a service that is not handling enormous numbers of simultaneous slow connections, that is fine. An ASGI/asynchronous service shines when a service holds *many* concurrent connections that are mostly *waiting* — many simultaneous clients, each request mostly spent awaiting a database or a downstream service — because the event loop overlaps all that waiting on few threads. The honest framing: ASGI is not simply "better"; it is the right choice for high-concurrency I/O-bound services and for the modern async ecosystem, and WSGI remains a perfectly sound choice for the large class of services that do not need it. Choose by the workload, as always.

## 17.4 The Framework Landscape

You do not write HTTP handling from scratch; you use a *framework*. Python has several, and a staff engineer should know the landscape and the basis for choosing.

**Flask** is the small, unopinionated, synchronous framework — a *microframework*. It gives you routing and request/response handling and very little else, leaving the choices (database layer, validation, structure) to you. Flask's virtue is its simplicity and its lack of imposed structure; it is excellent for small services, for prototypes, and for engineers who want to assemble their own stack. Its limitation is the flip side: for a large application, the structure Flask declines to impose is structure you must impose yourself, and not every team does it well.

**Django** is the large, opinionated, batteries-included framework — historically synchronous, now with async support. Django brings, in one package, an ORM, an admin interface, an authentication system, a templating engine, a migration system, and a great deal more, all designed to work together. Django's virtue is that for a certain large class of applications — particularly content-driven and database-heavy web applications — an enormous amount is already built and integrated, and a team can move very fast. Its cost is the weight and the opinionatedness: you get Django's way of doing things, and fighting it is painful, so Django is the right choice when its way is your way and the wrong choice when it is not.

**FastAPI** is the modern, async-native framework, and it is the one this chapter treats in most depth because it is, for new API services in particular, an excellent default and it embodies several of the book's threads. FastAPI is built on Starlette (a lightweight ASGI framework — Starlette is also usable directly when you want something more minimal) and on Pydantic (Chapter 6, Chapter 10). Its defining characteristic is that it is **type-driven**: you declare your request and response shapes as Pydantic models and type-annotate your handlers, and FastAPI uses those types to do, automatically, three things at once — *validate* incoming requests against the declared types (Chapter 6's trust-boundary rule, enforced by the framework), *generate API documentation* from the types, and *inject dependencies* into handlers. FastAPI's **dependency injection** is the Chapter 12 mechanism provided by the framework and provided well: a handler declares what it needs — a database session, the current authenticated user, a configuration object — as a typed parameter with a `Depends(...)` marker, and FastAPI constructs and supplies it, including resolving chains of dependencies. This is genuinely elegant: the architecture of Chapter 12 (decoupled components receiving their dependencies) is not something you bolt onto FastAPI; it is how FastAPI works.

Beyond these three: **Starlette** itself, for minimal async services; **Litestar**, another modern async framework; and others. But the working knowledge a staff engineer needs is the *basis for choosing* — Flask for small and unopinionated, Django for large and batteries-included where its opinions fit, FastAPI for modern type-driven async APIs — and the recognition that the choice is a real architectural decision with long-lived consequences, not a matter of taste.

## 17.5 The Hostile Environment, Part One: Timeouts and Pooling

Now the back half of the chapter, and its real substance: the operational concerns. This is where a service that works in a demo and a service that survives in production diverge, and it is the densest staff-level material in the chapter.

**The timeout. This is the most important paragraph in the chapter.** Every operation in a service that *waits on something external* — a call to a downstream service, a database query, a read from a network socket — *must have a timeout*. The reason is the chapter's spine made concrete: the network can simply *not answer*. The downstream service can be hung, the database can be overwhelmed, the connection can be silently dead — and an external operation with *no timeout* will, in those cases, *wait forever*. And a request handler stuck forever in a no-timeout call is not just one slow request; it is a *leaked resource* — a worker, a connection, an event-loop task — held indefinitely. Enough of them, and every worker is stuck waiting on the same hung downstream, and your service, which is itself perfectly healthy, stops answering *anything*. A missing timeout converts one slow dependency into a total outage of a healthy service. This is, genuinely, the single most common cause of production incidents in Python services, and the rule that prevents it is absolute: **every call to anything external has an explicit, finite timeout.** No exceptions. Not "usually." Every one. (This is the same rule Chapter 14 stated for `await`s and Chapter 19 will state for distributed calls — it recurs because it is that important.)

**Connection pooling.** Section 17.2 established that opening a connection costs a network round-trip. A service that opens a fresh connection — to its database, to a downstream HTTP service — for *every request* pays that round-trip every time, and under load it also tends to *exhaust* something: the operating system's available sockets, or the database's limit on simultaneous connections. The fix is a **connection pool**: a set of connections, opened once and *kept alive*, that requests *borrow* and *return* rather than create and destroy. A request takes a connection from the pool, uses it, returns it; the next request reuses it. Pooling removes the per-request connection cost and bounds the total number of connections. Modern HTTP clients and database libraries pool by default or make pooling easy — `httpx`'s client, the database connection pools of Chapter 18 — and a staff engineer ensures pooling is *configured* and *sized* deliberately rather than left to chance, because an unpooled or badly-pooled service has a performance and a stability problem waiting for load to expose it.

**HTTP clients.** A service is usually also a *client* — it calls other services. The Python landscape: `requests` is the classic synchronous HTTP client, simple and ubiquitous and entirely fine for synchronous code; `httpx` is the modern client offering *both* synchronous and asynchronous APIs (and it is the right choice in async code, because — Chapter 14's cardinal sin — a synchronous `requests` call inside a coroutine blocks the event loop); `aiohttp` is another async option. Whichever you use, the rules are the same and they are the rules of this section: use a pooled client (a persistent client object, not a fresh one per call), and set a timeout on every request.

## 17.6 The Hostile Environment, Part Two: Resilience Patterns

Timeouts and pooling are the foundation. Above them sit a set of named *resilience patterns* — standard responses to standard kinds of hostility. A staff engineer knows these by name and applies them deliberately. (Several recur, deepened, in Chapter 19, because they are fundamentally distributed-systems patterns; here they are introduced in the single-service context.)

**Retries.** A downstream call fails — but many failures are *transient*: a momentary network blip, a brief overload, a downstream instance that was restarting. For transient failures, *retrying* the call often succeeds. But retries must be done carefully, and the careful way has three parts. Retry only what is *safe to retry* — which means only *idempotent* operations (Section 17.7); retrying a non-idempotent operation can do the thing twice. Use *backoff* — wait longer between each successive retry (exponential backoff: 1 second, then 2, then 4) rather than retrying instantly, because instant retries just hammer a struggling downstream. And add *jitter* — randomize the backoff a little — because without jitter, if many clients all fail at the same moment (a downstream blip affects everyone at once) they all retry at the *same* backoff intervals, in synchronized waves, and those waves are themselves a load spike that can keep the downstream down. Retries with exponential backoff and jitter; never naive instant retries. (Chapter 19's War Story is the retry storm this prevents.)

**The circuit breaker.** Retrying helps a *transient* failure. But if a downstream is not transiently blipping but *genuinely down* — hard down, for minutes — then every request retrying it is just wasted effort and added load on a service that cannot answer. The *circuit breaker* pattern addresses this. A circuit breaker wraps calls to a downstream and *watches the failure rate*. When failures cross a threshold — the downstream is clearly down, not blipping — the breaker *opens*: it stops calling the downstream entirely and *fails fast*, immediately returning an error (or a fallback) without even attempting the call. After a cooling-off period it goes *half-open*, letting a trial request through; if that succeeds, the downstream has recovered and the breaker *closes* and normal calls resume; if it fails, the breaker opens again. The circuit breaker's value is twofold: it stops your service from wasting resources and time on a downstream that cannot answer (failing fast is better than timing out slowly, over and over), and it gives the struggling downstream *room to recover* by removing the load of constant retries.

**Backpressure.** A service can receive work faster than it can do it. If it simply *accepts* all the incoming work and *queues* it, the queue grows without bound, memory grows without bound, latency grows without bound, and eventually the service falls over — having accepted far more work than it could ever complete. *Backpressure* is the family of mechanisms by which a service *resists* being overwhelmed: it signals "I am full," it bounds its internal queues, it limits the number of operations it will have in flight at once (the bounded pool, the semaphore of Chapter 14). Backpressure means a service under excess load *degrades gracefully* — it does a bounded amount of work well — rather than accepting everything and collapsing.

**Load shedding and rate limiting.** Related to backpressure: when a service is overloaded, *load shedding* means deliberately *rejecting* some requests — fast, with a "try again later" response — so that the requests it *does* accept get handled properly. A service that sheds 20% of load under a spike and serves the other 80% well is far better than one that accepts 100% and serves all of it badly or collapses. *Rate limiting* is the related discipline of capping how many requests a given client (or in total) may make in a window — both to protect the service from being overwhelmed by one heavy or misbehaving client, and as a deliberate product policy. Both are about the service *controlling its own load* rather than passively absorbing whatever arrives.

**Graceful degradation.** When a *non-essential* dependency fails, a well-designed service does not fail the whole request — it *degrades*. If the recommendations service is down, the product page still loads, just without recommendations. If the enrichment service is down, the record is processed without the enrichment (Chapter 8's War Story — done *honestly*, with the degradation visible and logged, not silently). Graceful degradation is a *design* decision: it requires having decided, in advance, which dependencies are essential (the request genuinely cannot be served without them) and which are enhancements (their absence is a worse but acceptable response), and building the service so the loss of an enhancement does not take down the whole.

## 17.7 Idempotency and Graceful Shutdown

Two more concepts complete the operational picture, and both are about the service behaving correctly at its *edges* — the edge of a retry, and the edge of its own lifecycle.

**Idempotency.** An operation is *idempotent* if performing it *twice* has the *same effect* as performing it *once*. "Set this user's email to X" is idempotent — do it twice, the email is X, same as doing it once. "Add $10 to this account" is *not* idempotent — do it twice, the account has $20 more, not $10. Idempotency matters because of *retries* and, more broadly, because of the unreliable network. Consider: your service sends a request to a payment service; the payment service processes it; but the *response* is lost on the network. Your service never received a confirmation, so — reasonably — it *retries*. If the payment operation is not idempotent, the customer is charged *twice*. The network's unreliability means you can never be fully certain whether a request that you did not get a response to actually *happened* — and the only safe way to live with that uncertainty is to make operations *idempotent*, so that a retry, if the original actually succeeded, is *harmless*. The common mechanism is the **idempotency key**: the client generates a unique key for the operation and sends it with the request; the server records which keys it has already processed; if a request arrives with a key already seen, the server recognizes it as a retry of an operation it already did and returns the original result *without doing the operation again*. Idempotency is not an optional nicety; for any operation with real side effects in a system that retries (and every robust system retries), it is a *requirement*, and designing operations to be idempotent — or to have idempotency keys — is core staff-level service design. (Chapter 19 makes idempotency a central mandate of distributed systems; this is its first full statement.)

**Graceful shutdown.** A service does not run forever; it gets *deployed*, which means the running version is *stopped* so a new one can start (Chapter 21). How it stops matters. A *graceless* shutdown — the process is simply killed — abandons every request currently in flight: clients get errors, half-finished work is lost, the deploy is visibly disruptive. A *graceful* shutdown is a sequence: the operating system signals the process to stop (typically `SIGTERM`); the service, catching that signal, *stops accepting new requests* but *does not exit*; it *finishes the requests already in flight* (within a time limit); it *cleans up* — closes connection pools, flushes buffers, releases resources; and *then* it exits. Done right, a deploy is invisible to clients: in-flight requests complete normally, new requests go to the new version, nothing is dropped. Graceful shutdown is the service handling the edge of its own lifecycle correctly, and it connects directly to Chapter 14's cancellation contract (the in-flight async tasks must be cancellable and must respect cancellation) and to Chapter 21's deployment story (a rolling deploy depends on every instance shutting down gracefully). A service without graceful shutdown has a small, recurring outage built into every single deploy.

## 17.8 The Service as a Whole

Step back from the individual concerns to the picture they compose, because the picture is the staff-level understanding.

A production service is a program that has been *hardened against a hostile environment*. It sits behind a *load balancer* that spreads requests across multiple identical instances of it (possible because HTTP is stateless — Section 17.3). Each instance handles requests through a *framework*, with handlers kept thin (Chapter 12's layering — the handler translates HTTP to an internal call; the logic lives in the service layer). Every call it makes to anything external has a *timeout* and goes through a *connection pool*. Calls to downstreams are wrapped in *retries with backoff and jitter* for transient failures and *circuit breakers* for hard ones. The service applies *backpressure* and *load shedding* so excess load degrades it gracefully rather than collapsing it. Operations with side effects are *idempotent* so retries are safe. Non-essential dependencies can fail without failing the request — *graceful degradation*. And the service *shuts down gracefully* so that deploys are invisible.

None of that hardening is present in the demo version of the service. The demo has the handler and the happy path, and it works, on one developer's machine, with a benign network and a downstream that is always up. The gap between that demo and the production service is the entire content of Sections 17.5 through 17.7, and it is, almost exactly, the gap between a junior engineer's service and a staff engineer's. The framework is the easy part. The hostility is the job.

> ### War Story — The Missing Timeout That Took Everything Down
>
> A company ran a customer-facing web service — call it the main service — that, in the course of handling a request, made a call to a smaller internal service that supplied some supplementary information. The supplementary service was not critical; its data merely enriched the response. The call to it was a plain HTTP request, written early, in a hurry, with — as plain HTTP requests written in a hurry so often are — *no timeout*.
>
> For a long time this was invisible. The supplementary service was healthy, it answered in a few milliseconds, and the missing timeout never mattered, because the call always returned promptly on its own. The code had a latent defect, and the defect was dormant because the environment happened to be benign.
>
> Then the supplementary service had a bad day. Not a crash — a crash would almost have been kinder — but a *hang*: it stopped answering, while keeping its connections open. It accepted requests and then went silent. And every request to the main service, reaching the line that called the supplementary service, entered a network read with no timeout, and *waited*. Forever. Each waiting request held a worker. Within a short time *every worker* in *every instance* of the main service was stuck, blocked, waiting on the same hung supplementary service. The main service — which was itself perfectly healthy, whose own code had no bug, whose own dependencies (database, cache) were all fine — stopped answering *every request*, for *every customer*, because all of its workers were frozen waiting on a *non-critical* downstream that had merely gone quiet.
>
> A non-critical dependency had caused a total, customer-facing outage of a healthy service. The proximate fix during the incident was to forcibly cut off the supplementary service so the calls would fail fast and free the workers. The real fix was three things, each of which is a section of this chapter. A *timeout* on the call — so a hung downstream produces a slow request, not an infinite one, and the worker is freed. A *circuit breaker* — so once the supplementary service was clearly down, the main service stopped calling it at all and failed fast. And *graceful degradation* — so that a failed call to a *non-critical* service produced a response *without* the supplementary information, rather than a failed request, because the main service had been explicitly designed to know which of its dependencies were essential and which were enhancements.
>
> The lesson is the chapter's spine, paid for in a customer-facing outage. A service lives in a hostile environment. A downstream *will*, someday, hang. Code that assumes a benign network — code with a network call and no timeout — is not "code that works"; it is a latent outage, dormant only until the environment turns hostile, which it always eventually does. The single missing timeout was the whole bug, and "every external call has a timeout" is not a guideline. It is the rule that, had it been followed, would have turned a company-wide outage into a few slightly-degraded responses.

> ### The Level Line — The Network and the Web
>
> **A senior engineer** can build a working web service with a framework, knows HTTP, can call other services with an HTTP client, and knows that timeouts are a good idea.
>
> **A staff engineer** understands the full stack from socket to framework and why each layer exists; chooses among WSGI/ASGI and the frameworks deliberately by workload; treats the hostile environment as the core design problem — sets a timeout on *every* external call without exception, configures connection pooling, applies retries-with-backoff-and-jitter and circuit breakers and backpressure and load shedding as named deliberate patterns, designs operations to be idempotent, designs for graceful degradation, and implements graceful shutdown.
>
> **A principal engineer** designs services that are hardened by *construction* — where the hostile-environment patterns are the default structure and not an afterthought, where every dependency has been classified as essential or enhancement, where the failure modes have been thought through before the code is written; sets the team's standards for service resilience; and can teach the demo-versus-production distinction so the team builds hardened services from the first commit.

## 17.9 At the Interview Table

The network and the web are central to the *system-design interview*, and this chapter — with Chapters 18 and 19 — is its core preparation. The interviewer is watching whether you reason about the hostile environment or only about the happy path.

**The question: "Design a [URL shortener / rate limiter / notification service]" (a system-design opener).**

These open-ended prompts are not asking for the happy-path design — that part is easy and not what is being assessed. A strong candidate sketches the happy path quickly and then *spends the bulk of the time on the hostile environment*: "Here's the basic request flow. Now — the service has external dependencies, so every one of those calls gets a timeout and goes through a connection pool. Downstream calls get retries with backoff and jitter for transient failures, and a circuit breaker so a hard-down dependency makes us fail fast instead of piling up. The service applies backpressure — bounded queues, a cap on in-flight work — and sheds load under a spike rather than collapsing. Write operations carry idempotency keys so retries are safe. It runs as multiple stateless instances behind a load balancer, so any state lives in a shared store. And it shuts down gracefully so deploys don't drop requests." That structure — happy path briefly, then resilience thoroughly — *is* the staff-level system-design answer, and it is exactly what this chapter teaches.

**The question: "What happens if you don't set a timeout on a network call?"**

"In the normal case, nothing — which is what makes it dangerous. The call returns promptly and the missing timeout never shows. But the network can stop answering — a downstream hangs, keeps the connection open, and goes silent — and then a call with no timeout *waits forever*. Each waiting request holds a worker or a connection or a task. Enough of them on the same hung downstream, and every worker in every instance is frozen, and your service — which is itself perfectly healthy — stops answering everything. A missing timeout converts one slow dependency into a total outage of a healthy service. It's the most common cause of production incidents in Python services, and the rule is absolute: every external call gets a finite timeout, no exceptions."

**The question: "What's idempotency, and why does it matter for a service?"**

"An operation is idempotent if doing it twice has the same effect as doing it once — 'set the email to X' is idempotent, 'add $10' is not. It matters because of the unreliable network. If my service sends a request and the *response* is lost, I don't know whether the operation happened — so I retry, and if the operation isn't idempotent, I've now done it twice; the customer is charged twice. The network's unreliability means I can never be certain a request that I got no response to actually completed, and the only safe way to live with that is to make operations idempotent so a retry is harmless. The common mechanism is an idempotency key: the client sends a unique key, the server records keys it's processed, and a repeated key is recognized as a retry and returns the original result without re-doing the operation. For any operation with real side effects in a system that retries — and every robust system retries — idempotency is a requirement, not a nicety."

**The question: "WSGI or ASGI? Flask, Django, or FastAPI?"**

"WSGI is the synchronous interface, ASGI the asynchronous one — it's Chapter-13's CPU-versus-I/O decision in another form. A synchronous WSGI service handling concurrency with multiple worker processes is perfectly fine for many workloads; ASGI shines when the service holds many concurrent connections that are mostly waiting on I/O, because the event loop overlaps that waiting cheaply. For frameworks: Flask is small and unopinionated, good for small services and prototypes where I want to assemble my own stack; Django is large and batteries-included, excellent when its opinions match the application, especially database-heavy web apps; FastAPI is the modern type-driven async framework — Pydantic models drive validation, docs, and dependency injection automatically — and it's an excellent default for new API services. I choose by workload and by how well the framework's opinions fit the application; it's a real architectural decision."

**The red flags.** A system-design answer that is all happy path and never mentions timeouts, retries, failure, or scale. Not knowing why a missing timeout is dangerous. No concept of idempotency, or thinking it is exotic. Treating the framework choice as a matter of taste. And, generally, designing as though the network were reliable — the single clearest sign of an engineer who has built demos but not operated systems.

## 17.10 The Forge

**Drill 17.1.** Build a minimal web service with a framework of your choice — a couple of endpoints, request handling, JSON responses. Then go through it and add, explicitly, the production concerns: a timeout on every external call, a configured connection pool, structured handling of a downstream failure. Note for each what you added and why.

**Drill 17.2.** For each operation, state whether it is idempotent and, if not, how you would make it safely retryable: "create a user with this email"; "set this user's status to active"; "append this line to the log"; "charge this card $20"; "delete this record"; "increment this counter."

**Build 17.1.** Build a service endpoint that calls a downstream service, and make it fully hardened: a per-request timeout, retries with exponential backoff and jitter for transient failures, a circuit breaker that opens when the downstream is clearly down, and graceful degradation so that a downstream failure produces a degraded-but-valid response rather than a failed request. Then *simulate* the downstream being slow, then hung, then hard-down, and verify each pattern behaves as intended.

**Build 17.2.** Build a service with an idempotency-key mechanism: clients send a unique key with each write request, the service records processed keys, and a repeated key returns the original result without re-performing the operation. Test it by sending the same request twice (simulating a retry after a lost response) and confirming the operation happened exactly once.

**Investigate 17.1.** Take a running service (yours or a sample) and *attack* it: send it requests faster than it can handle, send it requests that hang, point it at a downstream that is down. Observe how it behaves under each kind of hostility. Then add backpressure and load shedding and observe the difference. Write up what an unhardened service does under load versus a hardened one.

**Investigate 17.2.** Implement graceful shutdown for a service: catch `SIGTERM`, stop accepting new requests, drain in-flight requests within a time limit, clean up resources, exit. Then test it: start a long-running request, send the shutdown signal mid-request, and verify the in-flight request completes rather than being dropped. Write up how this connects to a zero-downtime deploy.

**Design 17.1.** You are the staff engineer designing a customer-facing service that handles significant traffic, depends on a database and three downstream services (one of them critical, two of them enhancements), and must be deployable many times a day with no visible disruption. Write a three-to-four-page design document covering: the framework and WSGI/ASGI choice with reasoning; the request flow and the layering; the full set of resilience patterns and where each applies; which dependencies are essential and which are enhancements and what graceful degradation looks like for each; how the service scales (statelessness, load balancing); how it shuts down gracefully; and — explicitly — how the design would behave when each of its dependencies fails. This is the system-design interview rehearsed on paper, and Chapters 18 and 19 will deepen exactly this exercise with data and with distribution.
