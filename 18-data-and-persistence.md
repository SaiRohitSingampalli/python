## 18.1 The Question Behind the Chapter

A program's variables vanish when the process ends. A service's state must not — a user's account, an order, a posted message must survive the process that created them, survive deploys, survive crashes, and be there, correct, when the next request arrives, possibly on a different instance entirely. The mechanism for that survival is *persistence*, and persistence almost always means a *database*.

This chapter is about how a Python service stores and retrieves state correctly. It is a large topic and the chapter is correspondingly substantial, because data is where some of the most consequential decisions and some of the most common bugs in a real system live. By the end you will know how Python talks to a database at every level from the raw protocol to the ORM; you will know the one ORM bug — the N+1 query — that *every* engineer hits and how to recognize and prevent it; you will understand transactions and isolation well enough to reason about what happens when two requests touch the same data at the same time; you will know how to evolve a database's schema safely while the system runs; you will know when a relational database is the wrong tool and what the alternatives are; and you will understand caching, including the genuinely hard problem at its center.

A theme runs through all of it: **data is the part of a system that is hardest to change and most expensive to get wrong.** Code can be rewritten; a deployed bad schema, or corrupted data, or a migration that lost information, is a far harder thing to undo. Application code is forgiving; data is not. That asymmetry is why this chapter insists, more than any other, on care.

## 18.2 How Python Talks to a Database

There is a stack of abstractions between a Python service and a database, and a staff engineer understands every layer, because — exactly as with the socket-to-framework stack of Chapter 17 — the abstractions leak, and you cannot diagnose a problem at a layer you do not understand.

At the bottom is the **database driver** — a library that speaks the specific wire protocol of a specific database (`psycopg` for PostgreSQL, the various MySQL drivers, the standard library's `sqlite3`). Python standardizes the *interface* these drivers present, through a specification called the **DB-API**: it defines how you get a *connection*, how you get a *cursor* from it, how you *execute* a query and *fetch* results. Because of the DB-API, driver code looks broadly similar across databases — you connect, you execute, you fetch.

There is one rule at this level that is not a style preference but a *security requirement*, and it is the most important paragraph in the section. When a query needs to include a *value* — a user's email, an ID from a request, anything that came from outside — you must **never** build the query by *string formatting* the value into it. You must use *parameterized queries*: you write the query with a *placeholder* where the value goes, and pass the value *separately* to the execute call, and the driver inserts it safely.

```python
# CATASTROPHICALLY WRONG — SQL injection vulnerability
cursor.execute(f"SELECT * FROM users WHERE email = '{user_input}'")

# CORRECT — parameterized; the driver handles the value safely
cursor.execute("SELECT * FROM users WHERE email = %s", (user_input,))
```

The reason the first form is catastrophic is **SQL injection**. If `user_input` is an ordinary email, the string-formatted query is harmless. But if an attacker supplies, as `user_input`, a carefully crafted string containing SQL syntax — quotes and statement terminators and additional commands — then the string formatting *splices that SQL into your query*, and the database *executes it*. An attacker can, through an unparameterized query, read data they should not see, modify or delete data, or in the worst cases take control of the database. SQL injection has been one of the most exploited vulnerabilities in the history of software, and it is *entirely prevented* by parameterized queries: with a placeholder, the value is sent to the database *as a value*, never interpreted as SQL, and no crafted string can escape that. The rule is absolute, it admits no exceptions, and a staff engineer treats an unparameterized query with external input as a security defect on sight. (Chapter 22 returns to injection as a security topic; this is its first and most important statement, because it lives at the data layer where every engineer works.)

## 18.3 The ORM and SQLAlchemy

Writing raw SQL through the DB-API works, but for most application code it is verbose and it leaves a gap: SQL deals in rows and tables, your program thinks in objects. An **Object-Relational Mapper** — an ORM — bridges that gap: it maps database tables to Python classes and database rows to Python objects, so that your code creates, reads, updates, and deletes *objects*, and the ORM translates that into SQL.

In the Python world the dominant ORM, and the one this chapter treats as the default, is **SQLAlchemy**. SQLAlchemy is worth understanding as having two layers, because the distinction is genuinely useful. **SQLAlchemy Core** is a SQL *expression language* — it lets you build SQL queries programmatically, in Python, with composability and safety (parameterization handled), but still thinking essentially in terms of tables and queries. **The SQLAlchemy ORM** sits on top of Core and adds the object mapping — classes to tables, objects to rows. Many applications use the ORM; some use Core directly when they want the control of explicit SQL with Python's composability; and a staff engineer knows both exist and that you can drop from the ORM to Core (or to raw SQL) when a particular query is better expressed that way. (Django's ORM is the other major one — tightly integrated into Django, with the same essential concepts; the principles of this chapter apply to it equally.)

Two ORM concepts are worth naming because they explain a great deal of ORM behavior. The **session** (SQLAlchemy's term; Django calls the area of responsibility differently but the idea recurs) is the ORM's *unit of work* — it tracks the objects you have loaded and the changes you have made to them, and *flushes* those changes to the database as SQL, typically when you *commit*. The **identity map** is a related guarantee: within one session, a given database row is represented by *exactly one* Python object — load the same row twice and you get the same object, not two copies — which keeps your in-memory view of the data consistent. You do not have to think about these constantly, but when ORM behavior surprises you, the explanation usually lives in the session and the identity map.

The honest staff-level position on ORMs: an ORM removes an enormous amount of tedious, error-prone boilerplate and lets application code think in objects, and for the bulk of an application's data access that is a clear win. But an ORM is an *abstraction over SQL*, and like every abstraction it leaks — and the place it leaks most is performance, which is the entire subject of the next section. The mature stance is: use the ORM for the common cases where it shines, *understand the SQL it generates*, and be ready to drop to Core or raw SQL for the queries where the ORM's generated SQL is wrong for the job. An engineer who uses an ORM without ever looking at the SQL it produces is the engineer who ships the bug the next section describes.

## 18.4 The N+1 Query Problem

This section is short, and it describes the single most common performance bug in any system that uses an ORM. *Every* engineer hits it. A staff engineer recognizes it instantly, knows why it happens, and prevents it — and being able to explain it is one of the most reliable signals in a data-layer interview.

Here is the bug. You have a list of objects — say, a hundred blog posts — and each one has a related object — its author. You write the natural, innocent-looking code:

```python
posts = session.query(Post).all()        # ONE query: fetch the 100 posts
for post in posts:
    print(post.author.name)              # for EACH post, a query for its author
```

This looks fine. It is not fine. The first line is *one* query, fetching the hundred posts. But then the loop accesses `post.author` for each post — and the ORM, by default, *lazily loads* a related object the first time it is accessed, by issuing *a query for it right then*. So the loop issues *one query per post* — a hundred queries — to fetch the hundred authors. The total is *one query for the posts, plus N queries for the related objects* — **N+1 queries** — where one or two queries would have done.

The damage is severe and it scales with the data. A hundred posts is a hundred and one queries; ten thousand posts is ten thousand and one. Each query is a round-trip to the database (Chapter 17's expensive round-trip), so an endpoint that should take a few milliseconds takes seconds, and it gets *worse as the data grows* — the classic profile of a bug that passes every test on small data and falls over in production on real data. And it is *invisible in the Python code* — the code reads like ordinary attribute access; nothing about `post.author` announces that it is a database query. This is the ORM abstraction leaking exactly as Section 18.3 warned: the ORM made database access look like attribute access, and so it made a database round-trip look like a free operation, and the result is a hundred hidden round-trips in a loop.

The fix is to tell the ORM, *up front*, to fetch the related objects *together with* the main query — *eager loading* instead of lazy loading. The ORM provides the mechanism (SQLAlchemy's `selectinload` and `joinedload`, Django's `select_related` and `prefetch_related` — the exact names matter less than the concept): you declare "when you fetch these posts, also fetch their authors," and the ORM does it in *one additional query* (fetch all the needed authors at once with a single `WHERE author_id IN (...)`) or in a *join*, turning N+1 queries into one or two. The bug is fixed by changing how the data is loaded, not by changing the loop.

The deeper lesson, and the reason this tiny section carries such weight: **you must look at the SQL your ORM generates.** The N+1 bug is invisible in the Python and glaring in the SQL — a log of a hundred near-identical author queries is unmistakable. The defenses a staff engineer puts in place are exactly that visibility: develop with SQL query logging on, so you *see* the queries each endpoint issues; instrument production to *count* queries per request and alert when the count is anomalous; treat "this endpoint issues a number of queries proportional to the size of its result set" as a bug to be caught in review. The N+1 problem is not hard to fix. It is only hard to *see*, and seeing it is the skill.

## 18.5 Transactions and Isolation

So far the chapter has treated database access one operation at a time. But real operations are *composite* — "transfer money from account A to account B" is a *debit* and a *credit*, two changes that must *both* happen or *neither* happen — and real systems have *many requests touching the same data at the same time*. The database concept that makes both of those manageable is the **transaction**.

A transaction is a *group of operations treated as a single, atomic unit*. Its classic guarantees are summarized by the acronym **ACID**, and a staff engineer should know what the letters mean. **Atomicity** — the whole transaction happens, or none of it does; there is no partial state. If the money is debited from A and then the credit to B fails, atomicity means the debit is *rolled back* — the system never shows money having simply vanished. **Consistency** — a transaction moves the database from one valid state to another, respecting its rules and constraints. **Isolation** — concurrent transactions do not corrupt each other; each behaves, to a degree the next paragraphs make precise, as though it ran alone. **Durability** — once a transaction *commits*, its effects survive, even a crash. ACID is what a relational database *gives* you, and it is a large part of why relational databases are the default for data that matters.

The subtle letter is **Isolation**, because "concurrent transactions do not corrupt each other" turns out to be a *spectrum*, not a single guarantee, and the spectrum is defined by **isolation levels**. The reason there is a spectrum is a trade-off: *stronger* isolation means concurrent transactions interfere *less* — fewer anomalies — but it also means the database must do more locking or more work to keep them apart, which *costs performance*. So databases let you choose, per the needs of the operation, where on the spectrum to sit. The standard levels, from weaker to stronger, and the *anomalies* each one still permits:

**Read Uncommitted** — the weakest; a transaction can see *uncommitted* changes from another transaction (a "dirty read"), changes that might still be rolled back. Rarely what you want.

**Read Committed** — a transaction sees only *committed* data, but if it reads the same row twice, it might see *different* values, because another transaction committed a change in between (a "non-repeatable read"). This is the *default* in many databases and is adequate for a great deal of work.

**Repeatable Read** — within one transaction, re-reading a row gives the *same* value; the transaction has a stable view of the rows it has read.

**Serializable** — the strongest; the database guarantees that concurrent transactions produce a result *as if* they had run one after another, in some order — no anomalies at all. The strongest guarantee, the highest cost.

A staff engineer does not need every anomaly memorized, but does need to understand the *shape* of this: that "isolation" is a dial, that the default level permits *some* concurrency anomalies, and that for an operation where a concurrency anomaly would be a *correctness* problem — anything where two simultaneous requests reading-then-modifying the same data could produce a wrong result — you must either choose a stronger isolation level or use an explicit concurrency-control technique. The most important such technique is **optimistic concurrency control**: instead of locking a row while you read-modify-write it, you read it (noting a version number or timestamp), do your work, and then write *conditionally* — "update this row, *but only if* its version is still the one I read." If another transaction modified the row in between, the version no longer matches, the conditional write affects zero rows, and your code *detects the conflict and retries* rather than silently overwriting the other transaction's change. Optimistic concurrency is the standard pattern for the very common "two users edit the same thing at once" problem, and knowing it — knowing that the lost-update bug is real and that this is its fix — is core data-layer judgment. (This is the database-level cousin of Chapter 13's race condition: the same fundamental problem, concurrent access to shared mutable state, at a different layer.)

## 18.6 Schema Migrations

A database has a *schema* — the definition of its tables, columns, types, indexes, constraints. And a system's schema is not fixed: as the application evolves, the schema must evolve with it — a new column, a new table, a changed type, a new index. The question is *how* to make those changes, and the answer is one a staff engineer must hold firmly, because schema changes are among the most dangerous operations a system performs.

The naive answer — log into the production database and run an `ALTER TABLE` by hand — is wrong, and wrong in the way Chapter 11's hand-managed dependencies were wrong: it is unversioned, unreviewed, unreproducible, and impossible to apply consistently across the development, staging, and production databases. The right answer is **migrations**: schema changes expressed as *code*, *versioned in the repository* alongside the application code, *reviewed* like code, and *applied* by a tool in a defined order. SQLAlchemy's companion migration tool is **Alembic**; Django has migrations built in. A migration is a small, ordered, versioned unit of schema change, and the migration tool tracks which migrations a given database has had applied, so the same sequence of changes can be applied reliably to every environment.

But versioning the schema change is only half the discipline. The harder half is that a schema change on a *live, running system with real data* must be done *safely*, and "safely" has real content. Two principles:

First, **a migration must be backward-compatible with the currently-running code**, because of how deploys work (Chapter 21): for a window during a deploy, the *old* code and the *new* schema (or new code and old schema) coexist. If a migration drops a column that the still-running old code is using, the old code breaks during the deploy. The discipline this forces is the **multi-step migration** for any *breaking* change. To remove a column, you do not just remove it. You do it in stages across multiple deploys: first deploy code that no longer *uses* the column (but the column still exists); then, in a later deploy, actually remove the column. To rename a column, you do not rename it: you *add* the new column, deploy code that writes *both* and reads the new, *backfill* the new column from the old, deploy code that uses only the new, and *then* remove the old. Each individual step is backward-compatible with the code running alongside it. The breaking change is decomposed into a sequence of non-breaking ones. This is more work than a single `ALTER`, and it is the *correct* amount of work, because the alternative is an outage during every deploy that includes a breaking schema change.

Second, **a migration must not lock a large table for a long time.** Some schema operations, on some databases, *lock the table* while they run — and a lock on a large, busy table means every query against that table *waits* for the migration to finish, which on a multi-million-row table can be long enough to constitute an outage. A staff engineer knows which operations are cheap and which are expensive on the database in use, and for the expensive ones uses the safe techniques — adding a column in a way that does not lock, building an index *concurrently* (most databases support a non-locking index build), and, crucially, doing *data backfills* — populating a new column for millions of existing rows — *not inside the migration* but as a *separate, batched background job* that updates rows in chunks without holding a long lock or a long transaction.

The summary discipline: schema changes are code — versioned, reviewed, tool-applied; breaking changes are decomposed into backward-compatible multi-step sequences; and expensive operations on large tables use non-locking techniques and out-of-band backfills. Data is the hardest thing to change, and the schema is the structure of the data; a staff engineer treats schema migration with exactly the care that asymmetry demands.

## 18.7 When Relational Is the Wrong Tool

The relational database — PostgreSQL, MySQL, and the rest — is, and should be, the *default* for a system's data. It gives you ACID transactions, a powerful and standard query language, decades of operational maturity, strong consistency, and the ability to model complex related data with integrity. For most systems, for most data, "use PostgreSQL" is the correct, boring, right answer, and a staff engineer reaches for it by default and is suspicious of arguments to do otherwise.

But "default" is not "always," and a staff engineer also knows the cases where a different kind of data store is genuinely the better tool — and, equally, knows that those cases are *fewer* than the enthusiasm for "NoSQL" databases over the past decade sometimes suggested. The honest landscape:

**Key-value stores** — Redis is the dominant one — store simple values under keys with extreme speed, because they typically hold data *in memory*. Redis is rarely a system's *primary* database; it is overwhelmingly used *alongside* a relational database, as a *cache* (Section 18.8), as a store for ephemeral data like sessions, as a fast counter, and as a building block for rate limiting and queues. Its speed is the point, and its trade-off (data primarily in memory; durability is configurable but not its strength) is exactly why it is a companion store and not usually the system of record.

**Document stores** — MongoDB is the well-known one — store schemaless or flexible-schema documents (JSON-like structures). Their appeal is flexibility — no fixed schema, easy to store varied or nested data — and their cost is the flip side: the database does not enforce structure, so the discipline that a relational schema provides for free must be provided by the application, and complex queries across documents are often weaker than SQL's. A document store can be the right choice for genuinely schema-varied data, but a staff engineer is wary of choosing it merely to *avoid* schema discipline, because schema discipline is usually a feature, not a burden. (And the line has blurred: modern PostgreSQL has excellent support for JSON columns, so you can often get document-style flexibility *within* a relational database, keeping ACID and SQL.)

**Wide-column stores** — Cassandra and its kin — are built for *enormous* write-heavy workloads distributed across many machines, trading away some of the relational guarantees (notably, they typically offer weaker consistency — Chapter 19's territory) for the ability to scale writes horizontally to a degree relational databases struggle with. They are the right tool at genuine massive scale; they are over-reach for a system that does not have that scale.

**Specialized stores** exist for specialized shapes of data: search engines (Elasticsearch) for full-text search, time-series databases for metrics, graph databases for densely-connected data, object storage (S3 and its kin) for large files and blobs, and the embedded analytical and columnar stores. Each is the right tool when its specialty *is* your problem.

The staff-level judgment, stated plainly: **default to a relational database; reach for an alternative only when a specific, identified property of the workload genuinely demands it** — and be able to name *which* property. "We used a document store because it seemed modern" is not engineering; "we used Redis as a cache in front of Postgres because the read load on a few hot keys was the bottleneck, and we used a search engine for full-text search because SQL `LIKE` does not scale for that" is. The decade in which "NoSQL" was reached for reflexively taught the industry, expensively, that the relational default is the default for good reasons, and that abandoning it should be a deliberate decision with a named justification.

## 18.8 Caching and Its Hard Problem

A **cache** is a fast store of *copies* of data, placed in front of a slower source of truth, so that repeated reads of the same data are served quickly from the cache instead of expensively from the source. Caching is one of the most effective performance techniques in existence — a cache hit can be orders of magnitude faster than the database query it replaces — and a staff engineer reaches for it readily where the read pattern justifies it: a service with a small set of frequently-read, infrequently-changed data is an ideal caching candidate, and a Redis cache in front of the database (Section 18.7) is a standard, powerful pattern.

But caching has, at its center, a genuinely hard problem, and there is a famous half-joke in the field that names it: "there are only two hard things in computer science: cache invalidation and naming things." *Cache invalidation* — keeping the cache from serving *stale* data — is hard, and it is hard because of an inescapable fact: **a cache is a copy, and the moment the source of truth changes, the copy is wrong.** The cache now holds data that no longer matches reality, and every read served from that stale cache entry is a read of incorrect data. Managing that — deciding *when* and *how* a cache entry stops being trusted — is cache invalidation, and there is no perfectly clean answer; there are only strategies with different trade-offs.

The simplest strategy is **time-based expiration** — a **TTL**, a "time to live": each cache entry is trusted for a fixed duration and then automatically discarded, after which the next read goes to the source and re-populates the cache. TTL is simple and robust and very widely used, and its trade-off is explicit: for up to the length of the TTL, the cache *can* serve stale data. You tune the TTL to your tolerance — a short TTL means fresher data but more load on the source; a long TTL means less load but more staleness. For a great deal of data, "could be a few minutes stale" is perfectly acceptable, and TTL is then the right, simple answer.

When staleness is *not* acceptable, the strategy is **explicit invalidation** — when the source of truth changes, the code that changes it also *actively removes (or updates) the corresponding cache entry*, so the next read misses the cache and re-fetches fresh data. This keeps the cache fresher, but it is *harder*, because now *every* code path that modifies the data must remember to invalidate the cache, and a single forgotten invalidation is a bug that serves stale data indefinitely — and such bugs are notoriously hard to track down, because the code looks correct and the database is correct; only the cache is wrong.

Two more hazards a staff engineer must know. The **cache stampede** (or "thundering herd"): a popular cache entry expires, and in the brief moment before anything re-populates it, *many* concurrent requests all miss the cache *at once* and all hit the database *simultaneously* for the same data — a sudden spike of identical expensive queries that can overwhelm the source. The defenses are patterns like having only *one* request recompute the value while the others wait, or refreshing entries *before* they expire. And the general discipline: a cache is an *optimization*, and the system must be *correct without it* — the source of truth is the database, the cache is a performance copy, and the system's correctness must never *depend* on the cache being present or fresh. A cache that the system's correctness depends on is not a cache; it has quietly become a second, unreliable source of truth, and that is a bug.

The summary: caching is powerful and you should use it where the read pattern fits — but cache invalidation is genuinely hard, TTL is the simple robust default with explicit staleness, explicit invalidation is fresher but fragile, stampedes must be guarded against, and the system must remain correct if the cache vanishes. Reach for caching deliberately, with the invalidation strategy decided up front, not bolted on after.

## 18.9 The Repository Pattern and Decoupling from the Data Layer

A final structural point, tying this chapter back to Chapter 12. Application code that is *directly littered* with database queries and ORM calls — business logic interleaved with `session.query(...)` — is *coupled* to the data layer, with all the costs Chapter 12 named: it cannot be tested without a database, the persistence technology cannot be changed without touching business logic, and the two concerns (what the business does, how data is stored) are tangled.

The **repository pattern** is the standard decoupling. A *repository* is an object that *encapsulates the data access for a particular kind of thing* — an `OrderRepository` with methods like `get(order_id)`, `save(order)`, `find_pending()` — and presents that access through a *clean interface* (a `Protocol`, Chapter 10) expressed in the *domain's* terms, not the database's. The business logic talks to the repository's interface; the repository's *implementation* contains the actual ORM or SQL. Now the business logic depends only on the *abstraction* — and so it can be tested with an *in-memory fake repository* (Chapter 16's preferred test double), the persistence technology can change behind the repository's stable interface, and the two concerns are cleanly separated. This is Chapter 12's ports-and-adapters applied specifically to data: the repository interface is the *port*, the ORM-backed implementation is the *adapter*, and dependency injection supplies the adapter to the business logic. A staff engineer designing a system of any size routes data access through repositories, so that the data layer — the hardest thing to change — is at least *isolated* behind a clean seam.

> ### War Story — The Endpoint That Got Slower Every Week
>
> A team shipped a new endpoint — a dashboard view that listed a user's recent items, and for each item showed some related details: who created it, what category it belonged to, its current status. The code was clean, readable ORM code: fetch the items, then loop over them, and for each item access `item.creator`, `item.category`, `item.status_record`. It was reviewed, it was tested, it passed, it shipped.
>
> In the test environment, and in the first weeks of production, it was fast. Each test user had a handful of items; the endpoint returned in a comfortable few milliseconds. Then, slowly, it got worse. Not suddenly — *slowly*, week over week, as real users accumulated real items. An engineer eventually noticed the endpoint's latency on the dashboards had been climbing steadily and was now genuinely slow, and slowest for exactly the most active, most valuable users — the ones with the most items.
>
> The cause was the N+1 query problem, and it had been there since the first commit. The first ORM call fetched the user's items in one query. But the loop — `item.creator`, `item.category`, `item.status_record` for each item — lazily loaded each related object on access, issuing *a query per related object per item*. A user with ten items generated something like thirty-one queries; a user with three hundred items generated over nine hundred. Each query was a database round-trip. The endpoint's query count, and therefore its latency, was *proportional to how much data the user had* — invisible on the small data of tests and early production, ruinous on the large data of an established power user. And it was invisible *in the code*, because `item.creator` reads like free attribute access and gives no hint that it is a database query. The bug had passed review precisely because the reviewer, like the author, saw clean ORM code and not a hundred hidden round-trips.
>
> The fix was small once the cause was seen: tell the ORM to *eager-load* the related objects — fetch the creators, categories, and status records *along with* the items, in a couple of additional queries instead of N per item. The endpoint's query count dropped from "proportional to the user's data" to a small constant, and its latency dropped accordingly and *stopped growing*.
>
> The lesson is the chapter's. An ORM is an abstraction over SQL, and it leaks at performance: it makes a database round-trip look like a free attribute access, and so it makes the N+1 bug invisible in the Python and glaring only in the SQL. The defense is not cleverness; it is *visibility* — develop with SQL query logging on so you *see* the queries each endpoint issues, instrument production to count queries per request and alert on anomalies, and treat "this endpoint's query count grows with its result size" as a defect to catch in review. The N+1 problem is trivial to fix and famous for a reason: it is the bug every engineer ships once, because the ORM hides it so well, and a staff engineer is the one who has learned to *look at the SQL*.

> ### The Level Line — Data and Persistence
>
> **A senior engineer** uses an ORM competently, knows to use parameterized queries, understands that transactions exist, and can write a schema migration.
>
> **A staff engineer** understands the full stack from driver to ORM and reads the SQL the ORM generates; recognizes and prevents the N+1 problem instinctively; understands transactions and isolation levels and uses optimistic concurrency for the concurrent-modification problem; does schema migrations as versioned code with backward-compatible multi-step sequences and non-locking techniques for large tables; defaults to relational and can name the specific reason when reaching for an alternative; uses caching deliberately with a chosen invalidation strategy and an awareness of stampedes; and decouples business logic from the data layer with the repository pattern.
>
> **A principal engineer** treats data as the hardest and most consequential part of the system — designs the schema and the data architecture with the care its un-changeability demands, sets the team's standards for migrations and query review, makes the relational-versus-alternative and caching decisions with named justifications, and ensures the data layer is isolated behind clean seams so the rest of the system can change while the data stays safe.

## 18.10 At the Interview Table

Data-layer questions are central to both deep-dive and system-design interviews, and the N+1 question in particular is one of the most reliable depth probes that exists.

**The question: "What is the N+1 query problem?"**

A near-universal question, and the answer must be both mechanically precise and aware of the fix and the prevention. "It's the most common ORM performance bug. You fetch a collection — say a hundred posts — in one query, then loop over them accessing a related object on each, like `post.author`. The ORM lazily loads each related object on access by issuing a query right then — so the loop issues one query per post, a hundred queries, for what should be one. Total: one query plus N, N+1. It's severe because each query is a database round-trip, so the endpoint is slow and gets *worse as the data grows* — it passes tests on small data and fails in production on real data. And it's invisible in the Python, because `post.author` reads like free attribute access. The fix is eager loading — tell the ORM to fetch the related objects together with the main query, in one or two queries instead of N, with something like SQLAlchemy's `selectinload` or Django's `select_related`. The real defense is visibility: develop with SQL logging on so you see the queries, and instrument production to count queries per request. The deeper lesson is that you have to look at the SQL your ORM generates — the ORM hides the round-trips, and that's exactly why the bug is so common."

**The question: "How do you prevent SQL injection?"**

"Parameterized queries, always. You never build a query by string-formatting a value into it — `f\"... WHERE email = '{user_input}'\"` is the catastrophic form, because a crafted input containing SQL syntax gets spliced into the query and executed. Instead you write the query with a placeholder and pass the value separately to the execute call — the driver sends the value *as a value*, never interprets it as SQL, and no crafted string can escape. An ORM does this for you by default. The rule is absolute and has no exceptions; an unparameterized query with external input is a security defect."

**The question: "Explain database transactions and isolation levels."**

"A transaction is a group of operations treated as one atomic unit — it all happens or none of it does. The guarantees are ACID: atomicity (all-or-nothing, with rollback on failure), consistency (valid state to valid state), isolation (concurrent transactions don't corrupt each other), durability (a commit survives a crash). Isolation is the subtle one — it's actually a spectrum of levels, weaker to stronger, trading anomaly-prevention against performance. Read Committed, a common default, prevents dirty reads but still permits non-repeatable reads. Serializable is the strongest — concurrent transactions produce a result as if they'd run one at a time — and the costliest. The judgment is that the default level permits *some* concurrency anomalies, so for an operation where a concurrent read-modify-write could produce a wrong answer, I either raise the isolation level or use optimistic concurrency control — read with a version number, write conditionally on that version still matching, and detect-and-retry on conflict. That's the standard fix for the lost-update problem when two requests modify the same data."

**The question: "How do you safely add a column to a huge, live table?"**

"Two concerns. First, locking: on a large busy table, some schema operations lock the table and every query waits — that's an outage. I'd use the database's non-locking way to add a column, and if the column needs to be populated for existing rows, I would *not* do that backfill inside the migration — I'd do it as a separate, batched background job updating rows in chunks, so there's no long lock or long transaction. Second, backward compatibility: during a deploy the old and new code run side by side, so the change must be compatible with the currently-running code. Adding a *nullable* column is safe — old code ignores it. If it eventually needs to be non-nullable or replace something, that's a multi-step sequence across deploys: add it nullable, deploy code that writes it, backfill, deploy code that requires it, and only then add the constraint. Each step is backward-compatible; the breaking change is decomposed into non-breaking ones."

**The question: "When would you use something other than a relational database?"**

"My default is relational — PostgreSQL — because ACID, SQL, maturity, and strong consistency are the right baseline for data that matters. I reach for an alternative only for a specific, named reason. Redis as a cache or session store or rate-limiter, because its in-memory speed is the point and it sits *alongside* the relational database, not replacing it. A search engine like Elasticsearch for full-text search, because SQL `LIKE` doesn't scale for that. A wide-column store for genuinely massive write-heavy scale that a relational database struggles with. Object storage for large files. The judgment is that 'NoSQL because it's modern' is not a reason — the relational default is the default for good reasons — but a specific identified property of the workload is."

**The red flags.** Not knowing the N+1 problem, or knowing the name but not the mechanism. Building queries by string formatting. No real understanding of transactions or isolation. Treating schema migrations casually — not knowing the locking and backward-compatibility hazards. Reaching for NoSQL reflexively with no named justification. And caching with no thought given to invalidation — which signals an engineer who has used a cache but not operated one.

## 18.11 The Forge

**Drill 18.1.** Take a piece of code that builds SQL queries by string formatting and rewrite every query to be parameterized. Then, in writing, construct an example input that would exploit the original (string-formatted) version, and explain precisely why the parameterized version is immune.

**Drill 18.2.** Given an ORM code snippet that loops over a collection accessing related objects, identify whether it has an N+1 problem, count the queries it will issue for a result set of size N, and rewrite it with eager loading. Show the query count of the fixed version.

**Build 18.1.** Build a small service with a real database behind an ORM. Turn on SQL query logging. Write an endpoint that lists records with related objects, and *observe* the N+1 problem in the query log. Then fix it with eager loading and observe the query count drop. Write up the before and after.

**Build 18.2.** Implement optimistic concurrency control for a "two users edit the same record" scenario: a version column, a conditional update, and detect-and-retry on conflict. Write a test with two simulated concurrent editors and verify that one succeeds, the other detects the conflict, and no update is silently lost.

**Build 18.3.** Implement a cache layer in front of a database read, using a TTL strategy and then an explicit-invalidation strategy. For the explicit-invalidation version, write a test that catches the bug where a code path modifies the data but forgets to invalidate the cache. Then add protection against a cache stampede and demonstrate it.

**Investigate 18.1.** Take a real schema change — adding a column, adding an index, renaming a column — and write it out as a *safe migration plan* for a large live table: the migration steps, the deploy sequence, what is backward-compatible at each step, how any backfill is done out-of-band, and which operations would lock the table and how you avoid it.

**Investigate 18.2.** Refactor a piece of an application that has ORM calls scattered through its business logic into the repository pattern: define repository interfaces as `Protocol`s, move the data access into repository implementations, and inject the repositories. Then write tests of the business logic using in-memory fake repositories, with no database. Write up how the decoupling changed the testability.

**Design 18.1.** You are the staff engineer designing the data layer for a new system — pick a concrete domain (an e-commerce system, a content platform, a booking system). Write a three-to-four-page design: the schema and why; where you default to relational and where, if anywhere, you reach for an alternative store and the specific named reason; how transactions and isolation are handled for the operations where concurrency matters; the migration discipline; the caching strategy and its invalidation approach; how the data layer is decoupled from the business logic via repositories; and — explicitly — how the design protects against the data being corrupted or lost, since data is the hardest thing to fix. This is the data half of the system-design interview, and Chapter 19 will extend it to what happens when this data lives across many machines.
