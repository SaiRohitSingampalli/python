## 22.1 The Question Behind the Chapter

A system that is connected to a network is a system that is *under attack* — not metaphorically, not eventually, but continuously, from the moment it is exposed. Automated scanners probe every public service constantly; the question is never *whether* a system will be attacked but only whether the attack will *succeed*. And the consequences of a successful attack are not abstract: leaked customer data, stolen funds, a system turned to an attacker's purposes, legal liability, destroyed trust. Security is not a feature a customer asked for, and that is exactly why it is so often shortchanged — but it is, for a staff engineer, a non-negotiable part of building anything real.

This chapter is not a comprehensive security course; security is a deep specialty and a single chapter cannot make anyone a security expert. What this chapter *can* do, and what it is for, is install the *mindset* and the *working knowledge* that every staff-level engineer must have: the habit of thinking about how a thing could be abused, the catalog of the most common and most dangerous vulnerability classes and how to prevent each, the principles — defense in depth, least privilege, never trust input — that generalize beyond any specific attack, and the recognition that security is a *practice woven through everything*, not a layer added at the end.

The chapter has a thesis, and it is the most important security idea there is: **security is a property of the whole system and the whole process, not a feature.** You cannot build an insecure system and then "add security." Security comes from a thousand decisions made correctly throughout — every input validated, every secret handled right, every dependency vetted, every permission minimized — and a single one made wrong can undo all the others. A staff engineer carries security as a *constant background consideration*, the way they carry correctness, because that is the only way it actually gets done.

## 22.2 The Security Mindset

Before any specific vulnerability, there is a *way of thinking*, and it is the most transferable thing in the chapter. The security mindset is the habit of asking, of everything you build, not only "how is this used?" but **"how could this be abused?"**

An ordinary engineer, looking at a feature, thinks about the *intended* user doing the *intended* thing. A security-minded engineer additionally thinks about the *adversarial* user — someone deliberately, cleverly, patiently trying to make the feature do something it was not meant to do. They look at an input field and think "what is the *worst* string someone could put here?" They look at a URL parameter and think "what if I change this ID to one that is not mine?" They look at a file upload and think "what if this 'image' is not an image?" They assume every input is hostile, every boundary is being probed, every assumption is being tested by someone who *wants* it to be false.

This mindset has a structured form called **threat modeling** — systematically asking, of a system or feature, "what are the assets worth protecting, who might attack them, what are the possible attacks, and what defends against each?" A staff engineer does not need heavyweight formal threat modeling for every change, but does need the *instinct* it formalizes: when designing anything, spend a moment in the attacker's seat. The single most valuable security habit is simply *remembering to ask the question* — "how could this be abused?" — because most vulnerabilities ship not because the defense was hard but because no one thought to look for the hole.

## 22.3 Never Trust Input

If the chapter had to compress to one rule, it would be this: **never trust input.** *Any* data that originates from outside your program's own trusted core — a user's form submission, an API request body, a URL parameter, an uploaded file, a value from another service, even data read back from your own database if it was originally user-supplied — is *untrusted*, and untrusted data must be *validated* before it is used and *handled carefully* everywhere it flows. An enormous fraction of all security vulnerabilities reduce to a single root cause: *untrusted* *input was trusted.*

This connects directly to the *trust boundary* concept the book has developed since Chapter 6. A trust boundary is the line between your trusted internal code and the untrusted outside world, and the rule is that **at every trust boundary, input is validated** — checked that it is the right type, the right shape, the right size, within the allowed range, matching the allowed set. Chapter 6 gave the tool: at a trust boundary, a *Pydantic model* validates and coerces incoming data and rejects what does not conform, which is exactly why FastAPI's type-driven validation (Chapter 17) is a security feature and not merely a convenience. Validation at the boundary means malformed or malicious input is *rejected at the door*, before it can reach code that assumed it was well-formed.

The two main ways the next sections' vulnerabilities exploit untrusted input are worth naming as a pair, because the distinction organizes much of the chapter. The first is **injection** — untrusted input is allowed to *change the* *structure of a command* (a database query, a shell command, an HTML page) rather than being treated purely as *data*. The second is **broken access control** — untrusted input (a request) is allowed to *reach data or* *actions it should not*, because the system failed to properly check *who* is asking and *what they are allowed to* *do*. Injection is "the input became code"; broken access control is "the request reached what it shouldn't." Hold those two shapes; most of what follows is an instance of one or the other.

## 22.4 Injection

**Injection** is the vulnerability class where untrusted input is interpreted as *code* or *commands* instead of as *data*, and it has been, for two decades, one of the most exploited and most damaging classes of vulnerability in existence.

**SQL injection** is the canonical case, and Chapter 18 already taught both the vulnerability and the fix in full — this section reinforces it as part of the security picture. The vulnerability: a query built by *string-formatting* untrusted input into it, so that input containing SQL syntax *becomes part of the query's structure* and is executed — letting an attacker read, alter, or destroy data, or worse. The fix, absolute and complete: **parameterized queries** — placeholders for values, values passed separately, the driver guaranteeing the value is treated as *data* and never as SQL. An ORM does this by default. The rule admits no exceptions, and a staff engineer treats an unparameterized query with external input as a security defect on sight.

**Command injection** is the same disease in a different organ. If a program builds a *shell command* by string-formatting untrusted input into it and then executes it, an attacker can supply input containing shell syntax — a semicolon, a pipe, command substitution — and *their* commands run, with the privileges of your program. The defenses: *avoid* invoking the shell at all where you can; when you must run an external program, pass its arguments as a *list* (so each argument is a discrete item and cannot be interpreted as shell syntax) rather than as a single string handed to a shell; and never, ever build a shell-command string by formatting in untrusted input. Python's `subprocess` module, used correctly — argument lists, `shell=False` — is safe; used incorrectly — a formatted string with `shell=True` — is a command-injection vulnerability.

**Cross-Site Scripting (XSS)** is injection aimed at the *browser*. If a web application takes untrusted input and includes it in an HTML page *without proper escaping*, and that input contains a `<script>` tag or other active markup, then the attacker's script *runs in the browser of whoever views the page* — able to steal that user's session, act as them, exfiltrate their data. The fix is **context-aware output escaping**: any untrusted data placed into HTML must be *escaped* so that its characters are rendered as literal text, not interpreted as markup. Modern web templating engines (Jinja2 and the rest) do this **automatically by default** — auto-escaping — which is a major reason to use a templating engine rather than building HTML by hand, and a major reason that *turning auto-escaping off*, or building HTML strings manually, is dangerous. A related browser-side defense, **Content Security Policy (CSP)**, is an HTTP header that tells the browser to refuse to run scripts except from approved sources, limiting the damage even if an XSS hole exists.

The unifying principle across all injection — and this is the thing to *carry*, more than any specific fix — is: **keep code and data separate, and never let untrusted data cross into the code side.** A SQL query has structure (code) and values (data); injection happens when input crosses from the data side to the structure side. A parameterized query *enforces the separation*. An argument list *enforces the separation* for shell commands. Output escaping *enforces the separation* for HTML. Every injection vulnerability is a failure to keep that boundary, and every defense is a mechanism that *enforces* it. An engineer who internalizes "untrusted data stays data, always" has the principle from which every specific injection fix follows.

## 22.5 Authentication and Authorization

Two words that sound similar, mean different things, and are both essential — and confusing them, or doing either badly, is a major vulnerability category.

**Authentication** is establishing **who you are** — verifying identity. **Authorization** is establishing **what you are allowed to do** — verifying permission. Authentication is the login; authorization is the permission check on every subsequent action. A system needs both, and needs each done correctly.

On **authentication**, the single most important staff-level rule concerns *passwords*, and it is absolute: **never store passwords.** Not in plain text — which is catastrophic and, dismayingly, still happens — and not *encrypted* either, because encryption is reversible and a stolen key reverses it. Passwords are **hashed** with a *password-hashing algorithm* specifically designed for the purpose — bcrypt, scrypt, or Argon2 — algorithms that are *deliberately slow* (to make brute-force guessing expensive) and that *salt* each password (so identical passwords hash differently and precomputed-table attacks fail). You store the *hash*; when a user logs in, you hash what they typed and compare hashes; the actual password is never stored and, ideally, never logged or retained for an instant longer than the verification. A critical sub-point: do **not** use a fast general-purpose hash (like SHA-256) for passwords — fast is exactly wrong for password hashing, because fast means an attacker can guess billions per second; the purpose-built algorithms are slow *on purpose*. Beyond password storage: support **multi-factor authentication** (a second factor beyond the password) because it defeats a stolen password; and for service-to-service and modern authentication, know the standard protocols — **OAuth 2.0** and **OpenID Connect** — and the **token**-based mechanisms (such as JWTs) used to carry authenticated identity, rather than inventing your own authentication scheme, because authentication is exactly the kind of thing where rolling your own is a reliable way to ship a vulnerability.

On **authorization**, the most common and most damaging failure has a name — **broken access control**, and it consistently ranks at or near the top of the industry's lists of critical vulnerabilities. Its most frequent concrete form is the **insecure direct object reference**: a request includes an identifier — `/orders/9912` — and the system *fetches and returns that object* **without checking whether the requesting user is allowed to see it.** An attacker simply changes the number — `/orders/9913` — and reads *someone else's order*. The flaw is not exotic; it is *forgetting the permission check*, and it is everywhere because the "happy path" (a user viewing their own order) works perfectly without the check, so the missing check is invisible until someone goes looking. The defense is discipline: **every request that accesses a resource or performs an action must check that the authenticated user is authorized for that specific resource or action** — and the check must be on the *server*, never trusting the client, because anything the client enforces the client can bypass. A staff engineer reviewing code watches for the access-control check specifically, because its *absence* looks exactly like correct code.

The principle underneath authorization is **least privilege**: every user, every service, every component, every credential should have the *minimum* permissions needed to do its job, and *no more*. A service that only needs to read from a database gets a read-only credential. A component that only needs one capability is granted only that one. Least privilege does not *prevent* a compromise, but it *contains* one: if a least-privileged component is breached, the attacker gains only that component's minimal permissions, not the keys to everything. Least privilege is one of the highest-leverage security principles because it limits the *blast radius* of every other failure.

## 22.6 Secrets and Data Protection

Systems hold things that must be protected — credentials, and the data itself — and a staff engineer must know the rules for both.

**Secrets** — passwords, API keys, tokens, certificates, encryption keys, database credentials — were addressed in Chapter 21 from the deployment side; here is the security framing. The absolute rule: **secrets never appear in source code and never appear in the repository.** A secret committed to version control is permanently compromised — it lives in the repository's history forever, visible to everyone with repository access, surviving even a later "deletion" because history retains it — and the *only* true remedy for a leaked secret is to *rotate* it (replace it with a new one). Secrets live in a dedicated **secrets manager** — a system built to store them encrypted, control and audit access to them, and rotate them — and are supplied to the application *at runtime*. Beyond storage, two more secret disciplines: secrets should be **rotated** regularly and *especially* immediately on any suspicion of exposure (which is why a secret leak is survivable — you rotate); and secrets must never be **logged** (Chapter 20's rule) — a secret in a log is a secret leaked to everyone with log access. Automated **secret scanning** — tooling that checks every commit for things that look like credentials — is the safety net, because committing a secret by accident is genuinely easy.

**Data protection** is about the user data the system holds, and the framing is **encryption in two states**. *Encryption in transit* means data moving across a network is encrypted — in practice, **everything uses TLS** (HTTPS); plain unencrypted HTTP for anything real is not acceptable, because the network is not private (a fallacy from Chapter 19) and unencrypted traffic can be read or altered in flight. *Encryption at rest* means data sitting in storage — databases, disks, backups — is encrypted, so that someone who obtains the raw storage cannot read the data. Both are expected baselines for a real system. Beyond encryption: **data minimization** — the most secure data is the data you *never collected*; collect only what you genuinely need, keep it only as long as you need it, and you shrink both the harm of a breach and your compliance burden. And a staff engineer is aware that data protection is not only an engineering concern but a *legal* one — regulations such as GDPR impose real obligations about consent, retention, deletion, and breach disclosure — and that "we hold personal data" carries responsibilities that reach beyond the code.

## 22.7 The Supply Chain

A modern Python application is *mostly not your code*. It is your code plus a deep tree of third-party dependencies — and their dependencies, and theirs (recall Chapter 11's dependency tree). Every line of all of that code runs with your application's privileges. This is the **software supply chain**, and it is a security frontier that has grown sharply in importance, because attackers have learned that compromising a *widely-used* *dependency* compromises everyone who uses it — a far better return than attacking one target.

The threats are concrete. A **malicious package** — published deliberately to do harm, sometimes under a name *typo-squatting* a popular package (a name one keystroke away from a real one, hoping for a mistyped install). A **compromised legitimate package** — a real, trusted package whose maintainer account was breached, or to which a malicious contribution was slipped, so that a version you *upgrade into* now contains an attack. And **known vulnerabilities** — a dependency with a publicly-disclosed security flaw that you have simply not yet updated away from.

The defenses a staff engineer puts in place:

**Pin and lock dependencies** — the *lock file* of Chapter 11, with exact versions and cryptographic hashes, so that what you install is *exactly* what was reviewed and tested, and a dependency cannot silently change underneath you. The hashes specifically defend against a package being swapped for a tampered one.

**Scan dependencies for known vulnerabilities** — automated tooling (`pip-audit` and others) checks your dependency tree against databases of disclosed vulnerabilities and tells you which of your dependencies have known flaws. This belongs *in the CI pipeline* (Chapter 21), running on every change, so a newly-disclosed vulnerability in a dependency is surfaced promptly. **Update deliberately** — keep dependencies reasonably current (an old dependency accumulates unpatched vulnerabilities), but update *with* the lock file and the tests and a real review, not blindly.

**Vet what you add** — before adding a new dependency, consider whether it is genuinely needed (each dependency is attack surface), and whether it is reasonably maintained and reputable. The most secure dependency is the one you did not add.

The supply chain connects back to Chapter 11's trusted publishing and to Chapter 21's container scanning (the *base image* of a container is itself a dependency with its own vulnerabilities, and container images get scanned too). The overarching point: a staff engineer's security responsibility extends past their own code to *all the code* *their system runs*, and that means the supply chain is something to be actively, tool-assisted, continuously managed — not assumed safe because "it's a popular package."

## 22.8 The Principles That Generalize

Specific vulnerabilities change; new attack classes emerge; the details of this chapter will age. What does *not* age is a small set of *principles* — and a staff engineer holds the principles, because the principles generate the right answer even for attacks the chapter never named.

**Defense in depth.** Never rely on a *single* security control. Assume any one defense *can* fail — and arrange that when it does, *another* defense is still standing. Validate input at the boundary *and* use parameterized queries *and* run with least privilege *and* encrypt the data: if one layer is breached, the others still protect. A system whose security depends on one perfect control is a system one mistake away from compromise; a system with layered, redundant defenses survives the inevitable individual failure.

**Least privilege.** Already met in Section 22.5: every component, credential, user, and service gets the *minimum* access needed and no more. It does not prevent breaches; it *contains* them. It is the principle that bounds the blast radius of everything else.

**Never trust input** — Section 22.3. All external data is hostile until validated.

**Fail securely.** When something goes wrong — an error, an unexpected state, an exception — the system should fail into a *safe* state, which means a *closed*, *denied* state. If an authorization check errors out, the result must be *denied*, not *allowed*. A system that, when confused, *grants* access has failed *open*, and failing open is how an error becomes a breach.

**Keep security simple and visible.** Complex security mechanisms are *themselves* a source of vulnerability — they are hard to get right and hard to review. Prefer simple, well-understood, *standard* mechanisms over clever custom ones, which leads to the next principle.

**Do not roll your own — especially cryptography.** Cryptography is extraordinarily easy to get *subtly* wrong in ways that look fine and are catastrophically broken. The rule is absolute: **do not implement your own cryptographic algorithms or protocols.** Use established, audited libraries (in Python, the `cryptography` library; the standard library's `secrets` module for generating secure random tokens — and *not* the ordinary `random` module, which is *not* cryptographically secure). The same caution extends to authentication and other security-critical mechanisms: use the standard, audited, battle-tested implementation, because the custom one will have the flaw that the standard one had found and fixed years ago.

**Security is a process, not a state.** A system is never "secure" as a finished condition. New vulnerabilities are discovered, dependencies develop flaws, the system changes, attackers evolve. Security is *ongoing* — continuous scanning, regular updates, periodic review, staying informed. A staff engineer treats security as a practice that never finishes, woven into the regular work, not a milestone that gets checked off.

These principles are the durable core. Memorize the OWASP Top Ten if you like — it is a genuinely useful, regularly-updated list of the most critical web vulnerabilities, and a staff engineer should be broadly familiar with it — but the *principles* are what let you reason about the vulnerability that is *not* on any list yet.

> ### War Story — The ID You Could Just Change
>
> *A company's web application let users view their own records — orders, documents, account details. The* *relevant pages worked the obvious way: the URL contained the record's identifier — *`/documents/4471`* —* *and the server, receiving the request, looked up document 4471 and returned it. The feature had been built* *quickly, it worked perfectly in every test, and it had been in production, untroubled, for a long time. Every test* *passed because every test did the intended thing: a logged-in user viewing their own document, which the* *code handled flawlessly.*
>
> *What the code did not do was check ownership. It received a document ID, and it fetched and returned that* *document — full stop. It never asked the question "is the user making this request actually allowed to see* *this particular document?" The happy path did not need the check — a user viewing their own document got* *the right result without it — so the missing check was completely invisible. The code looked correct. It read* *like correct code. It was correct, for the only scenario anyone had tested.*
>
> *Then someone — it could have been a curious user, a security researcher, or an attacker — noticed the ID* *in the URL and did the obvious adversarial thing: they changed the number. *`/documents/4472`*. And the* *server, having no ownership check, dutifully looked up document 4472 — which belonged to a different user* *entirely — and returned it. The discovery was trivial; from there, an attacker could simply iterate — 4473,* *4474, every number — and walk straight through every document of every user in the system. A serious* *data breach, exposing other people's private records, and the vulnerability was not a sophisticated exploit of* *some subtle flaw. It was the absence of an *`if`* statement. The system had been one missing permission* *check away from a breach since the day the feature shipped.*
>
> *The fix was small: every endpoint that fetched a record by ID now first checked that the record belonged to* *(or was otherwise permitted to) the authenticated user, and denied the request if not — on the server,* *unconditionally. But the lessons were larger than the fix. First, this is ***broken access control / insecure direct object reference***, and it is near the top of the industry's critical-vulnerability lists because it is so easy* *to ship — the happy path works without the check, so nothing draws attention to its absence. Second, it is* *exactly what the ***security mindset*** is for: an engineer who had paused to ask "how could this be abused?"* *— who had looked at that ID in the URL and thought "what if I change it?" — would have found the hole in* *seconds, before any attacker did. The defense was not technically hard; the defense was thinking to look.* *And third, it is why a staff engineer reviewing code watches specifically for the authorization check, treating* *its absence as a defect — because a missing access-control check is the rare bug that is invisible precisely* *because the code that lacks it looks completely fine.*
>
> ### The Level Line — Security
>
> **A senior engineer*** knows the common vulnerabilities, uses parameterized queries, hashes passwords,* *knows to use HTTPS, and does not commit secrets.*
>
> **A staff engineer*** carries the security mindset — habitually asks "how could this be abused?" — and knows* *the major vulnerability classes and the defense for each; never trusts input and validates at every trust* *boundary; does authentication and authorization correctly, watching specifically for broken access control;* *handles secrets and data protection properly; actively manages the supply chain; and reasons from the* *durable principles — defense in depth, least privilege, fail securely, don't roll your own crypto.*
>
> **A principal engineer*** makes security a property of the team's whole process — threat modeling in design,* *security review in code review, dependency and secret scanning in the pipeline, the principles as standards* *— treats security as an ongoing practice rather than a milestone, ensures the system is built with defense in* *depth so no single failure is fatal, and instills the security mindset across the team, because security is a* *thousand correct decisions and one engineer cannot make them all.*
>
## 22.9 At the Interview Table

Security questions appear in system-design rounds, in deep-dive rounds, and increasingly as their own focused interview. They test the *mindset* and the *principles* more than memorized exploits.

**The question: "How do you prevent SQL injection?"** (and the broader "what is injection?")

"SQL injection is one instance of a general class — injection — where untrusted input is allowed to become *code* instead of staying *data*. For SQL specifically: never build a query by string-formatting input into it, because input containing SQL syntax then becomes part of the query and gets executed. Always use parameterized queries — placeholders for values, values passed separately — so the driver guarantees the input is treated as data, never as SQL; an ORM does this by default. The same principle covers the whole class: command injection is prevented by passing arguments as a list instead of a shell string; XSS is prevented by escaping untrusted data before it goes into HTML, which templating engines do automatically. The unifying rule is keep code and data separate and never let untrusted data cross to the code side."

**The question: "How should passwords be stored?"** "Never stored as anything reversible — not plain text, and not encrypted, because encryption can be reversed with a stolen key. Passwords are *hashed* with a purpose-built password-hashing algorithm — bcrypt, scrypt, or Argon2 — which are *deliberately slow*, to make brute-force guessing expensive, and which *salt* each password so identical passwords hash differently. You store the hash; at login you hash the input and compare. Critically, you do *not* use a fast hash like SHA-256 — fast is exactly wrong, because fast lets an attacker guess billions per second. And I'd add multi-factor authentication, since it defeats a stolen password, and I'd use standard protocols rather than inventing my own auth scheme."

**The question: "What is broken access control?"**

"It's allowing a request to reach data or actions it shouldn't, by failing to check *what the requester is allowed to* *do* — and it's near the top of the industry's critical-vulnerability lists. The classic form is the insecure direct object reference: a request has an ID, like `/orders/9912`, and the server fetches and returns that object *without checking the user owns it* — so an attacker just changes the number and reads other people's data. It's so common because the happy path works fine without the check — a user viewing their own order — so the missing check is invisible; the code looks correct. The defense is discipline: every request accessing a resource checks that the authenticated user is authorized for that *specific* resource, on the server, never trusting the client. And underneath it is least privilege — minimum permissions everywhere — which contains the damage when something does get through."

**The question: "How do you think about dependency security?"**

"A modern app is mostly *not* my code — it's a deep tree of dependencies, all running with my privileges, so the supply chain is real attack surface. The threats are malicious packages, including typo-squats; legitimate packages that get compromised; and dependencies with known, disclosed vulnerabilities I haven't updated past. The defenses: pin and lock dependencies with a lock file including hashes, so what installs is exactly what was reviewed and can't change underneath me; scan the dependency tree for known vulnerabilities with tooling like `pip-audit`, in CI, on every change; update deliberately, with tests and review, keeping things reasonably current; and vet what I add, because each dependency is attack surface and the most secure dependency is the one I didn't add."

**The question: "Walk me through how you'd think about security for a new service."**

A strong answer leads with mindset and principles, not a checklist: "I'd start with the security mindset — for each feature, ask not just how it's used but how it could be *abused*, a lightweight threat model: what's worth protecting, who'd attack it, how. Then the concrete practices: never trust input — validate everything at the trust boundary, ideally with typed models; prevent injection by keeping code and data separate everywhere; authentication with proper password hashing and standard protocols, and authorization checked on every resource access, watching specifically for broken access control; secrets in a secrets manager, never in code or the repo; TLS in transit and encryption at rest; dependency scanning in the pipeline. And I'd reason from the durable principles — defense in depth so no single failure is fatal, least privilege to contain blast radius, fail securely so errors deny rather than grant, and don't roll my own crypto. Security isn't a feature I add at the end; it's a property of every decision, and an ongoing practice, not a finished state."

**The red flags.** No security mindset — never thinking adversarially. Trusting input. Not knowing the major vulnerability classes or their defenses. Storing passwords reversibly, or with a fast hash. No concept of broken access control — often *the* most revealing gap. Secrets in code. Rolling one's own cryptography. And treating security as a feature to bolt on rather than a property of the whole system and process.

## 22.10 The Forge

**Drill 22.1.** Take a piece of code with several security vulnerabilities planted in it — an unparameterized query, a shell command built from input, a missing authorization check, a logged secret, a password stored with a fast hash. Find every vulnerability, name its class, and fix each correctly.

**Drill 22.2.** For each, apply the security mindset and write down how it could be abused and how you would defend it: a search box; a URL with a record ID; a file upload; a "reset password" flow; an endpoint that takes a callback URL; a field that gets displayed back on a page.

**Build 22.1.** Build a small web service with correct authentication and authorization: passwords hashed with a proper algorithm, sessions or tokens handled correctly, and — on *every* endpoint that accesses a resource — a server-side check that the authenticated user is authorized for that specific resource. Then write tests that act as an attacker: try to access another user's resource by changing an ID, and confirm it is denied.

**Build 22.2.** Take a service and harden it end to end: validate all input at the boundary with typed models; ensure every query is parameterized; move every secret out of the code into runtime configuration; add TLS; add dependency vulnerability scanning to its pipeline. Document each change and which principle or vulnerability class it addresses.

**Investigate 22.1.** Run a dependency vulnerability scanner (`pip-audit` or similar) against a real project. For each vulnerability it finds, investigate: what is the flaw, how severe, is the project actually exposed to it, what is the fix? Write up what the exercise revealed about the project's supply-chain exposure.

**Investigate 22.2.** Study the current OWASP Top Ten. For each item, write two or three sentences: what the vulnerability is, and how — concretely, in a Python service — you would defend against it. This builds the working catalog a staff engineer is expected to carry.

**Design 22.1.** You are the staff engineer responsible for the security of a system that handles sensitive user data and money. Write a three-to-four-page security design: the trust boundaries and how input is validated at each; authentication and authorization, including how broken access control is prevented; secrets management; data protection in transit and at rest, and data minimization; supply-chain management; how security is built into the team's process — threat modeling, security review, pipeline scanning; and how the durable principles — defense in depth, least privilege, fail securely — shape the architecture. This is the staff-level exercise: security as a property of the whole system and the whole process, designed in deliberately.
